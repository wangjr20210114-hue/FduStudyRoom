## 为什么不能直接复制为网页登录

以下是针对本项目架构的判断：

- 旦挞是在设备上替用户访问学校已有业务；我们的后端还要为不同用户保存预约、审批和工单，必须独立确认请求身份。
- 浏览器提交“已登录”、学号、学生类别或角色不能作为证明；后端仍需取得和校验可信学校结果，随后才签发本系统 Cookie。
- 若直接采用学号密码代理，通常是 Vue 把凭据交给 Java，由 Java 访问学校认证及用户信息服务。这样本系统后端会接触学校密码，需要另行确定处理方式，不能沿用“只在学校页面输入密码”的说明。
- 若只在本机工具完成登录，再让本机报告成功，仍缺少后端可验证的身份结果；增加桌面壳本身不能解决这一点。
- 姓名或成功访问一卡通服务不单独证明当前具有学生资格；普通用户仍须核验 STUDENT 与有效状态，工号管理员、维护人员仍须本系统预授权。
- 当前审查的旦挞登录分支对教职工类型尚未执行同样的验证流程；不能直接据此认定我们的工号管理与维护场景已覆盖。

## 两条路线

| 项目 | 学校正式跳转接入 | 先评估旦挞方式的本地原型 |
| --- | --- | --- |
| 目标 | 完成现有网站的正式身份认证 | 确定本人授权账号在当前学校环境下能否认证并取得可信身份 |
| 密码位置 | 用户在学校页面输入，本系统不接收 | 原型在本机处理；若之后改为集中式后端代理，需要明确接受这一架构变化 |
| 前提 | 学校为本项目确认协议、登记回调及属性 | 本人或获准测试账号、可用网络、正常验证码及二次认证处理路径 |
| 身份依据 | 服务端验证学校回调结果和属性 | 需要逐项确认学校响应是否足以证明用户标识、身份类型及有效资格 |
| 当前可认定的结果 | 尚未具备项目接入资料 | 仅有源码可行性线索，尚无真实账号验证结果 |
| 推荐用途 | 现有网站的正式路线 | 范围明确的可行性验证，不直接当作生产登录验收 |

当前向用户确认路线，尚未选择密码代理或开始收集学校凭据。无需把密码、密钥或学校会话发到聊天中。
