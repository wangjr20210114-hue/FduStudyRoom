# 数据边界、实际触发与中断恢复

需求或测试涉及集合、分页、刷新、多步写入时，设计用例前读取本文件。
要测哪几个等价类见 `equivalence-classes.md`；本文件只管样本怎么选、分支怎么触发。
Spec 已要求的结果属于必需验收；额外边界标为补充，预期不明确时先记录依据或假设。
本文件规定选择边界和验证恢复的方法，不预设业务结果或实现步骤。

## 1. 数据要能触发目标行为

先核对真实机制：下拉刷新、滚到底加载、向下滑动和分页不是同一件事。
确定手势、容器是否需要内容溢出、页容量和服务返回条件，再准备数据。
短列表可刷新时不用强行凑两页；需要溢出时，记录内容高度大于视口的证据。

每个分支保存：

| 项目 | 记录内容 |
|---|---|
| 初态 | 页面、实体身份、真实数量、页容量或当前中间状态 |
| 目标条件 | 怎样才会进入这一分支 |
| 操作 | 真实入口、手势、请求或受控故障 |
| 触发证据 | 滚动位移、刷新状态、回调、请求增量、故障位置日志等 |
| 结果 | 场景 ID、实际值、原始证据；未触发时的原因 |

“按钮点过”“脚本没有异常”不能证明分支已触发。
数据或外部条件无法准备时记 BLOCKED；测试操作或故障注入出错时记 ERROR。
初态、操作和观察器正确，产品未执行 Spec 要求的行为时记 FAIL，
并保留“未触发”的观察结果，不能把产品不响应统一算作数据不足。
不涉及分支触发的纯计算或静态检查写“不适用”并说明原因。

## 2. 数量等价类的样本选择

数量等价类的具体样本这样选：

- 分页按真实页容量 p 选 p−1、p、p+1、2p+1；p=1 时合并重复数量。p 取自边界事实，不靠估。
- “多条”至少 2 条且身份可区分，能看出顺序、重复和误删。
- 虚拟列表的可见节点数不等于总数，用服务、存储或完整遍历核对。

- 每个等价类都要写触发条件与触发证据（见第 1 节）；条件不具备记 BLOCKED，不记 PASS。
- 按需求确定操作的影响范围，核对目标对象的变化和不应变化的部分，不能只检查容器存在。

## 3. 多步写入：阶段表与幂等恢复

先从当前代码、接口约定和需求确认写入分几步、每步写哪里、失败后留下什么，再沿阶段选中断点。
每个阶段一行：

| 阶段 | 写入位置 | 中断后残留 | 重入时应能 | 幂等断言 |
|---|---|---|---|---|
| <1> | <数据库 / 文件 / 缓存 / 服务> | <半成品记录、孤立文件、不一致计数> | <识别并清理，或跳过已完成阶段> | <重试两次的结果与一次相同> |

中断点按阶段选：

1. 第一步尚未产生状态变化。
2. 某一步已完成，后续步骤尚未完成。
3. 所有状态变化已完成，但结果响应或界面确认尚未完成。

恢复的判据不是“有没有报错”，而是**能不能重入并最终成功**。
事务或原子操作不允许出现的状态不强行构造。

在隔离测试数据上用可控方式中断，保留证明故障位置的证据。
测试不得提前写好最终正确结果。无法命中目标位置时说明缺口，不能报该恢复分支通过。

解除故障后，按实际恢复机制重新进入、保留数据重启或重试原操作。
核对各步骤的真实状态、影响范围及后续可用性；完成、撤销、重试或报错的预期，
以需求、接口约定或已说明的数据一致性依据为准，不默认所有操作采用同一种恢复方式。
超时可能发生在状态已经变更之后，先查真实结果再判断重试。
同一操作重试两次的结果必须与执行一次相同；去重、幂等键和补偿逻辑都按这个判据检查。
Spec 未规定重复操作行为时标为歧义，不自行假定。

清库、清浏览器存储或删除容器卷会清除正在验证的状态，不能用这些动作替代恢复测试。
每次故障只改变一个主要条件，取证后恢复本例配置并清理本例数据。

## 4. 验证测试能发现问题

已确认旧缺陷有可复现版本时，用独立初态重跑，检查对应断言是否失败。
没有旧版本时可在临时副本对已确定的断言做少量受控修改，检查测试能否发现预期违背。
记录人为修改和结果，不把它当成真实缺陷，本项目按 AGENTS 对每条完成需求保留独立变异验证，实际命令见 [TDD 协议](../../campus-tdd/references/protocol.md)。
用于修改规则的案例与最后验证效果的案例分开；以缺陷检出和误报评估，不能只看通过率。
