# 检查方案：划分等价类并决定每类怎么测

当前场景进入 Red、写测试代码前读取本文件。输入是 analysis.json 的场景原文与对象对应、
待实现 objects、边界事实。每个场景产出一张表：要测哪几个等价类、每类怎样算对、用什么测试、怎么测。
需求分析完成（问题已问完）后，写入 analysis.json 对应场景的 cells，记录说明见 §2，字段映射见 §4。
预期只来自场景原文；原文没写的口径回到需求问题表问人，测试不自行补。

## 1. 步骤

1. **划分等价类**：按 `equivalence-classes.md` 以数据为主、补少量界面状态，`#1` 固定为常规情况（happy path），
   引用写 `S01#2`。每个等价类写**怎样算对**和依据（原文引用 / 问题表 ID 待确认）。
2. **选测试类型**：每个等价类至少映射到一个测试，按“怎样算对要看哪里”选：

   | 怎样算对 | 测试 |
   |---|---|
   | 要在界面上看：显示、内容、跳转、持续、变化 | UI 测试 |
   | 只是逻辑结果：计算、过滤、排序、格式化 | 单元测试即可 |
   | API 权限、契约、数据约束、持久化 | API / 数据库 / 契约测试 |
   | 有界面行为的常规情况 `#1` | 必须有 UI 交互测试，从场景入口走到原文结果；纯后端场景检查对应公开 API 或数据约束 |
   | 界面状态类（`界面：…`） | UI 测试，复用 `#1` 的初态和观察，中间插入该操作 |
   | 入口类（`入口：…`） | UI 测试，从该入口出发，按 `#1` 的观察与比较判定 |

   结论在界面上、但数据在界面上造不出（如超过页容量要上百条）时，逻辑用单元测试证明，
   UI 测试至少测一个能造出的样本，并在“测试”列写明理由。两层不重复证明同一结论。
3. **选样本和初态**：数据条数、入口路径、采样窗口；数量等价类的样本按 `boundary-and-recovery.md` §2 选。
   身份、数量和状态要足以区分正确与错误结果；标明来源（真实链路 / 夹具 / 自造 / 本地会话），
   mock 与本地会话只证明该条件下的行为。双源数据两边都要备齐。
4. **定观察位置**：查实际 DOM / 可访问性树、源码符号、模型、接口或响应，记录属性 / 字段路径。
   已有对象用实际定位；待实现对象用 objects 的约定 key。需求用词不能直接当选择器。
5. **定比较方法**：按“怎样算对”选精确值、关系式（包含、同步、递增、幂等、往返一致）或不变式。
   “持续 / 递增 / 同步”要连续采样，单帧快照不能证明；不能把内容、身份要求降为存在性判断。
   运行中捕获的 ID 记录取值位置和代表的对象；时间戳、耗时等偶然值不固化为预期。

某个等价类测不了写理由：`拿不到`（条件造不出）、`待确认`（口径未定）或 `已授权不测`，空白不算理由。

记 `拿不到` 前先在授权的隔离环境构造：测试数据库记录、本地服务或浏览器可上传的夹具文件，写明已试动作。
不能伪造真实账号、权限、外部接口或生产数据。仍造不出就按 [向人提问](../../campus-workflow/references/human-decision.md)
提出供给类问题，最晚在当前场景（合并实现时为当前轮）结束时问；人回复前该等价类保持 BLOCKED。
人工同意暂不测的单列豁免与影响，不把它计为自动测试 PASS；正式验收范围改变须走批准基线。
进入 Red 前核对被测输入、容器和服务版本；测错版本的结果不能归为需求失败。

## 2. 记录

需求分析完成、问题表里的待确认项都已问过后，在 analysis.json 当前场景的 cells 写入“测试检查方案”。
需求阶段不写这部分；测试阶段不改场景原文和对象对应，测试中发现的新问题照常登记；已固定 analysis 时先在私有记录保留，再 reset 后更新分析，不在旧检查点下静默改写。

```markdown
### S01 测试检查方案

| # | 等价类 | 怎样算对 | 依据 | 测试 | 样本与初态 | 观察与比较 | 状态 |
|---|---|---|---|---|---|---|---|
| 1 | 常规：3 首歌，字段齐全 | 迷你播放器持续显示歌名和歌手；进度时间播放中持续递增 | 原文"显示歌名和歌手""持续递增" | UI：S01-UI01 | 导入 3 首本地歌，播放第 1 首 | 歌手 Text（C11）3 秒内每 200ms 采样均存在且等于歌手名；进度时间（C12）间隔 2 秒两次采样，后值 > 前值 | 已核对 |
| 2 | 歌手字段为空 | 显示约定的占位文本 | Q03 待确认 | UI：S01-UI02 | 导入 1 首无歌手标签的歌 | 歌手 Text（C11）；文本等于占位 | 待确认 |
| 3 | 0 首 | 显示空态提示，无残留 | Q02 已确认 | UI：S01-UI03 | 清空曲库 | 空态文本节点；文本等于提示 | 已核对 |
| 4 | 时长 ≥ 10 分钟 | 进度时间按 "mm:ss" 显示 | Q01 已确认 | 单元：S01-UT01（纯格式化逻辑） | 时长 625 秒 | formatTime 返回值；精确等于 "10:25" | 已核对 |
| 5 | 界面：切后台再回来 | 同 #1：回到前台后歌名歌手仍显示，进度继续递增 | 原文"持续递增" | UI：S01-UI04 | 同 #1，播放中按 Home 停 5 秒再回到应用 | 同 #1 的 C11 采样与 C12 两次采样；回来后第一次进度值 > 离开前 | 已核对 |
```

缺少观察器或数据时保留该等价类和缺口，继续其他等价类；观察器与初态正确而目标未实现时可建立 FAIL，
不要求先实现新功能才写 Red。

## 3. 生成与执行

1. 复用已验证的准备、等待、取证和清理结构，生成范围限于当前检查方案。
2. 生成后逐个等价类回读“怎样算对”，确认代码确实落实了比较方法、能区分正确对象与其他对象。
   能编译、有 assert、运行器 OK 都不等于覆盖。
3. 实际运行按 [TDD 协议](../../campus-tdd/references/protocol.md) 保存结果，每条断言记录所属等价类。
   未触发按原因记 FAIL / ERROR / BLOCKED，未运行记 NOT_RUN，都不计 PASS。
4. Green 使用与 Red 相同的等价类和预期；口径经人确认后改变时，先更新检查方案，再重建相关证据。

## 4. 本项目记录映射

上表说明分析方法，不要求新增一份 Markdown 分析文档。

| 表列 | analysis.json / 私有证据 |
| --- | --- |
| # | cells.id：<执行场景ID>#<序号> |
| 等价类、怎样算对 | cells.expected（写明该类与具体结果） |
| 依据 | criterion + basis，basis 逐字等于批准 acceptance；详细原文引用可另附 source_quote |
| 测试 | kind + test_ids，来自真实框架发现结果 |
| 样本与初态 | sample |
| 观察与比较 | observation + comparison |
| 状态 | 运行后保存到私有 runs / 收据；不原地修改已固定 analysis |

设计模式完成 cells 与 test-plan 后返回 TDD，运行模式才写代码和执行。
当前可用框架、实际 record 参数和 UI 缺口见 [Web 与后端测试接口](web-adapter.md)。
原模板的播放器样例仅说明观察与比较方法，不是自习室需求。
