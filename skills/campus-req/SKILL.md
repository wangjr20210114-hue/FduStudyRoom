# 需求澄清

## 目标

先把本轮已批准的需求**全文逐字**收进分析快照，包括背景、约束、风格、说明等非场景部分；
再把 Spec 分成场景清单。每个场景三件事：**逐字原文**、**关联页面 / 组件**（用边界事实里的稳定 key）、
**需要新实现的对象进待实现表**。原文优先：需求就是原文，不润色、不扩展；原文没写的口径进问题表，不自行补。
本阶段只做需求解析和仓库理解，不含测试设计；等价类、定位、数据和取证都在测试阶段完成。
需求分析完成后，由测试阶段在 analysis.json 各场景的 cells 中追加“测试检查方案”，本阶段不写这部分。

## 执行条件

- 已明确认证成员、模块、前后端层和本轮需求；只读分析可按用户授权进行，施工须有工作单和模块容器。
- 读取 AGENTS、spec/modules.json、spec/requirements.json；代码、测试、字典、迁移只写 manifest 白名单。
- 本次沿用参考的分析步骤，输出适配现有 analysis.json；字段映射见 [分析约定](references/analysis.md)。

## 输入

1. **批准需求与来源**（必填）— spec/requirements.json 本轮条目、任务书对应原文及已有用户决定。
2. **源码仓库路径**（必填）— 本模块工程及允许读取的公开契约。
3. **边界事实**（必填）— 总流程的边界确认产物，见 [边界确认](../campus-workflow/references/boundary.md)。
4. **业务场景草案与已有观察**（可选）— spec/spec-network.json、spec/specs/、实际文件与观察；草案不能覆盖批准验收。
5. **已有分析**（恢复必填）— spec/progress/<模块key>/<层>/analysis.json；沿用稳定 ID。

## 执行流程

### Stage 1: 收录全文并分场景

**先收录全文**：按 [原文与场景映射](references/source-and-scenarios.md) 用程序读取本轮批准条目，
在 analysis.json 的 source_snapshots 保存路径、摘要和完整原值；需求行的 id/source/acceptance 原样保留。
任务书保留原 PDF 摘要、页码与实际摘录，用户补充保留来源，不把转述称为 PDF 逐字原文。
非场景部分（背景、目标、界面风格、数据说明、限制、注意事项等）不用逐段分析，
在索引中列出它们的段落位置，标“实现时参考”；其中可验收的约束不得遗漏。

**再分场景**：**一个已有原文场景章节 = 一个场景**，不把多个字段机械拆成多个场景。
已建立的 Sxxx.SCxx 业务场景沿用编号与“场景概述 / 操作步骤与预期结果”原文；
执行工具使用 <需求ID>.S01…，用 business_scene_refs 关联，两套 ID 不相互覆盖。
涉及多个批准需求时按需求建立执行记录并关联同一业务场景，不由一个需求的失败代表其他需求。
没有场景章节时按完整功能行为分场景，记明依据；影响验收的新口径记问题表，不能擅自加入批准清单。

每个场景**逐字引用该章节全文，不改一个词**——改词就制造一个名称差异问题。
**不按条目拆**：章节里的多个入口、多个信息项、多条结果都留在同一个场景里，
由测试阶段在检查方案里切成等价类或写进“怎样算对”。场景是实现单元，拆得过碎会让开发和回归变乱。

### Stage 2: 需求名词对应页面 / 组件

读取边界事实，把场景原文里的**界面名词**逐个对应到边界事实的页面 / 组件：

```markdown
| 对象 | 教室列表→实际路由；教室名称→实际组件 key；保存按钮→实际稳定 key |
```

- 左边是需求原文原词，右边是边界事实的稳定 key；原文的界面名词都要有对应，多个用 `、` 分隔。
- 对不上（界面里在、叫法不同）不臆造 key，差异记入问题表，对应仍写真实 key。
- 原文名词在边界事实表里没有 → 先确认是不是没采到（不可达、条件未满足、采样不足）；
  是采样缺口就记问题表，**不直接当成要新实现**；确认原文要求且实现缺失的，进 Stage 3。

### Stage 3: 待实现组件 / 页面表

把待实现项写入 analysis.json 场景的 objects（结构见 [分析约定](references/analysis.md)），
只把**已确认需要新实现**的对象标为 missing，沿用稳定 key：

- 需求要求一个页面而界面里没有 → 一个页面对象，status=missing；
- 需求要求一个页面上没有的控件 → 一个组件对象，所属页面填那个页面（页面本身可以是待实现的）。
- 每行写清：**名称**（需求原词）、**约定 key**（实现时设置的组件标识 / 页面路由名，测试按它定位）、
  类型、所属页面、触发场景、依据（原文位置 + 已排除入口与采样缺口的说明）；后端同时对应 API、表或约束。没有待实现项就写“无”。
- 测试设计检查点固定 analysis 后，原始对象事实不原地改写；实现状态记入私有运行证据并关联原 key。若需改方案，先 reset 相应检查点再重建证据。

### Stage 4: 标注问题并回查原文

歧义、不一致、归因统一记入问题表（Q / U / A 三类，见 [分析约定](references/analysis.md)）：

- **`[AMBIGUOUS]`**：只有 Spec 另一处原文**直接给出答案**时，状态写 `原文可定`，结论里逐字引用那句原文；
  其余一律 `待确认`，到 Stage 5 问人。以下都**不能**当自定依据：现有代码或实现表现、惯例常识、
  其他 App 的做法、"两种都支持"式的合并解释、方便测试。
- **`[UNRESOLVED]`**：需求与提交物或基线不一致，写明实际状态与解除条件；不删未实现的需求。
- **`[ATTRIBUTION]`**：前置缺失与本轮未实现分不清时，先做可执行诊断，诊断结果写进描述。
  要用 mock、本地会话等替代条件继续的，结论写授权来源（人的回复 `H` 编号或任务说明原文）；
  没有授权来源就是 `待确认`。`已确认` 只用于有人回复或任务说明原文作依据的情况。

自查 `原文可定`：把结论里的原文引用去掉，剩下的部分如果还在规定什么（格式、范围、点击区域、状态含义），
那部分就是自己补的，改为 `待确认`。

最后从原始 Spec 逐段回查：每个场景都有原文引用，入口、限制、时间关系没有被漏掉；场景依赖和执行顺序明确。
非场景部分里如有可独立验证、却没被任何场景覆盖的要求，记入问题表（是否当场景处理），不自行升格为场景。

### Stage 5: 问人并等回复

问题表里有 `待确认` 项时，一次问完：按 [向人提问](../campus-workflow/references/human-decision.md)
先给摘要表，再逐项用人话写，每个 H 的末行「依据」注明对应的问题表 ID。
只将受影响需求登记为 clarification 受阻，不带着待确认的口径进入该需求的测试阶段；其他独立需求继续。
等候期间不把超时当同意，不代替人回复。

收到回复后：问题表状态改 `已确认`，结论写回复要点、H 编号及原始回复位置；更新受影响分析。
已有 test-plan 时按执行协议使后续检查点失效并重建。没有待确认项时直接交给 campus-test。

## 输出

- analysis.json：批准需求快照、逐字场景原文、初态/动作/预期、对象关联、待实现项、问题和执行顺序。
- 可进入测试设计、已验收核对后跳过、受阻及待协调的条目；不直接改权威需求、业务 spec 或公共契约。

场景原文和批准验收是预期的出处；测试阶段按场景 ID 引用，划分等价类时不新增原文之外的预期。
旧任务里的断言详情、元素清单保留，按既有 ID 继续，不要求重写历史。

## 完成条件

- [ ] 来源快照与原文件 / 条目一致，非场景部分的位置已列出并标“实现时参考”。
- [ ] 已有业务场景与执行场景可相互追溯，没有把一个章节机械拆成多个场景或重编号。
- [ ] 每个场景有逐字原文；原文的界面名词逐个对应真实 key，没对应的进了问题表或待实现清单。
- [ ] 名称差异进了问题表，需求用词没被改写；采样缺口没有被当成待实现。
- [ ] 待实现项写清名称、约定 key、类型、所属页面、触发场景和依据；不写跨模块内部实现。
- [ ] 歧义和不一致已登记；每个 `原文可定` 都逐字引用了原文，结论没有超出引用的内容。
- [ ] 没有拿代码、惯例或合并解释当依据；用替代条件继续的写了授权来源。
- [ ] 可推进项没有待确认的验收口径；受阻项保留真实问题和解除条件，不能称已澄清。
- [ ] 已按原文顺序回查；覆盖与依赖明确，requirements 检查点通过后交给测试阶段。
