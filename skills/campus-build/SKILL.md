# FduStudyRoom 环境构建

## 目标

让成员在Windows或macOS取得正确源码，复用或补齐环境，构建并启动主应用或协作缓冲站，交付可访问地址和真实验证结果。缺少IDE时给出安装提示；不把搭环境扩展成业务开发。

环境检查、工具补齐、构建及运行按 [阶段细则](references/stages.md) 执行。
初始化完成后复用已有环境，日常只检查变化和目标构建，不每次重复安装。

## 执行条件

- 用户要求首次搭环境、修复环境、构建/运行项目，或campus-workflow进入环境准备阶段。
- 能访问项目源码及官方安装来源；不能获取、安装或启动的步骤保留为受阻，不伪造成功。
- 已有工程、兼容工具和持久化数据优先复用，不停止其他项目、不重置数据库。

## 输入

| 输入 | 必需性与取得方式 |
| --- | --- |
| 工作区路径 | 默认当前目录；未克隆时使用独立新目录 |
| 构建目标 | 主应用或缓冲站；总流程调用时沿用其目标 |
| 源码及版本 | 已有仓库优先；远程为https://gitee.com/wangjr2021/fdu-study-room.git，必须包含优化基线 |
| 操作系统、架构、现有工具和端口 | 自动检测，不要求成员手动填写版本表 |
| 本机配置 | 读取已忽略配置；缺少时按角色和授权创建，不输出密钥 |
| 是否启动 | 要求“跑起来”时构建并启动；明确只构建时不加--start，启动阶段记NOT_RUN |

## 执行要求

读取项目AGENTS、manifest及 [阶段细则](references/stages.md)。普通缺项通过受信源和可用权限补齐，下载校验摘要；IDE缺失只提示。初次Docker许可、虚拟化、重启和超出权限的安装需要真实人工处理。不得改动锁文件、公共技术栈或其他项目环境来让本机构建通过。

## 执行流程

### Stage 0：定位工作区与目标

**执行**：定位包含spec/modules.json和scripts/team.py的项目根目录，记录commit、脏状态及目标。没有源码时克隆到未占用的新目录；版本缺少本技能所需文件时报告版本问题。

**输出**：仓库路径、版本、工作区状态、主应用/缓冲站目标。

**通过条件**：源码可读取且版本满足入口要求；未覆盖已有目录或未提交改动。

### Stage 1：检查宿主环境与IDE

**执行**：检查系统/架构、磁盘、目标端口和IDE。检测不到IDE时提示安装或由用户确认，不替用户安装IDE。

**输出**：宿主检查结果、IDE提示及端口占用归属。

**通过条件**：构建资源可用，所需端口属于本项目或空闲；IDE提示已明确，不把IDE不可检测伪称已经安装。

### Stage 2：检查与补齐构建工具

**执行**：检查Git、入口Python3.12+、Node24、Java21。优先复用兼容工具或项目隔离工具，从受信源补缺，不改系统默认Java。Python入口缺失时使用scripts/build.ps1或sh scripts/build.sh引导安装；macOS仅复用已有Homebrew等受信渠道，不运行未知远程安装脚本。

**输出**：实际工具版本、路径、安装/复用结果。

**通过条件**：本目标所需工具可执行，实际版本符合manifest；权限或下载问题有明确诊断，失败不冒充完成。

### Stage 3：准备Docker与Compose

**执行**：检查CLI、Compose和引擎连通；已有WSL引擎直接复用。需要安装时使用官方来源；成员严格沙箱按manifest核对引擎能力。

**输出**：可响应的引擎、Compose和隔离能力结果。

**通过条件**：所需容器能力可用。缺虚拟化、许可、重启或权限时暂停依赖阶段，记录人工操作与复检方法。

### Stage 4：核对源码与更新条件

**执行**：核对技术栈、锁文件和Maven Wrapper。需要更新源码时只对干净工作区执行git pull --ff-only；脏工作区保留，不做reset、自动stash覆盖或解决冲突。Windows UNC目录优先使用已有稳定映射或迁至本机目录，不争抢后台服务使用的盘符。

**输出**：可构建源码版本、更新结果或保留原因。

**通过条件**：没有覆盖用户工作、改变锁文件或越过Git冲突；源码与目标基线一致。

### Stage 5：准备本机配置

**执行**：复用或生成本项目密码、服务认证键、端口和可选初始化管理员配置，仅写已忽略位置。测试使用当前工作区独立的 PostgreSQL 和测试邮箱配置，与应用库、缓冲站业务库分开；测试端口仅绑定本机并自动分配。缓冲站成员配置由获授权的协调人维护，普通成员复用自己的凭据。

**输出**：私有配置位置及配置就绪状态，内容不公开。

**通过条件**：目标所需配置齐备，未将凭据写进Git或交付日志，未覆盖已有持久化数据。

### Stage 6：安装锁定依赖并构建

**执行**：安装前端锁定依赖，先等待独立测试数据库和测试邮箱健康，再按目标运行后端Maven Wrapper verify及前端测试、类型检查和build。测试环境变量只用于本次验证，不沿用外部业务库地址。无论验证成功或失败，结束后只释放本工作区的测试容器，保留测试数据卷与私有日志。主机与容器依赖缓存分开，不混用原生依赖。命令入口可用team.py build；没有成功构建不进入启动。明确只构建时完成本阶段后直接输出报告，不执行Stage 7—8。

**输出**：各构建命令、退出码、测试服务健康与释放结果、测试/类型检查结果和产物。

**通过条件**：当前目标构建与要求的检查全部通过；编译、依赖或测试失败保留实际stage和日志。

### Stage 7：启动数据库并核验迁移

**执行**：启动本项目独立PostgreSQL，复用持久化卷并等待就绪；核验启动时Flyway迁移与各模块历史。正式种子与演示业务数据分离，不改已发布脚本。

**输出**：数据库就绪、迁移及种子执行结果。

**通过条件**：目标数据库可用、迁移成功；主应用库与缓冲站工具库隔离，没有清空或重建已有业务数据。

### Stage 8：启动目标服务

**执行**：启动当前已实现的后端/前端或缓冲站，后台进程隐藏窗口并使用私有日志。重复运行识别并复用本项目进程，不停止占端口的其他项目。

**输出**：目标服务地址、进程归属和日志路径。

**通过条件**：所需进程存活并进入可健康检查状态；未实现业务不伪装已开放。

### Stage 9：真实检查与交接

**执行**：要求启动时运行目标健康/API冒烟；仅构建时汇总构建结果和未启动状态。汇总Stage结果。主应用入口为 `python scripts/team.py build --install --start`；缓冲站由协调人init-buffer后使用 `python scripts/team.py build --buffer --install --start`。脚本实际合并执行多个动作时仍按真实日志归类，不把命令发出当成阶段通过。

**输出**：可访问地址、版本、检查结果、日志和外部受阻项。

**通过条件**：本次请求范围内的检查实际通过；未跑的macOS、浏览器或生产发布单列，失败时保留材料和数据，不宣称系统已跑通。

## 输出

- 每个Stage的PASS/FAIL/ERROR/BLOCKED/NOT_RUN及依据。
- 复用/安装的工具与实际版本、源码版本、服务地址、日志位置。
- 缺失IDE提示及需要人处理的权限、许可、网络、虚拟化或重启条件。

## 完成条件

- [ ] 源码版本、工具版本、配置与目标已经核对。
- [ ] 目标构建、测试和类型检查通过，相关产物来自当前源码。
- [ ] 要求启动时，目标数据库和服务实际启动且健康/API检查通过；仅构建时明确目标应用没有启动，独立验证服务已释放。
- [ ] 没有覆盖其他项目环境、用户未提交工作或持久化数据。
- [ ] 未完成和未验证项如实列出；构建完成不被描述成业务开发、正式发布或Git推送完成。
