# TDD 编码

## 目标

在本模块工程目录内按实现轮次执行 Red→Green→Refactor，保存阶段快照与测试结果，
完成需求实现和分级回归。按场景循环与阶段判据执行，正式提交仍走人工验收后的缓冲站。

## 执行条件

- 认证身份、模块、前后端层、冻结基线与可写工作树明确，模块容器可用。
- 总流程 workspace / baseline / requirements / test-plan 已通过；单独调用也须先满足这些前置。
- 已完成项检查真实证据后跳过，无法核验的记录缺口，不把缺证据等同缺功能。
- 读取 AGENTS、spec/modules.json、spec/requirements.json。使用 TypeScript/Vue 3、Java 21/Spring Boot 4.1.2、PostgreSQL。
- 代码、测试、API 封装、中英字典、迁移只写 manifest 路径；公共依赖、锁文件和已发布迁移冻结，不跨模块写库或引用内部实现。

## 输入

1. **工程目录路径**（必填）— 当前成员、模块及层对应的 worktree 与容器。
2. **需求分析**（必填）— analysis.json，含来源快照、稳定场景 ID、逐字场景原文、初态/动作/预期与 cells。
   实现时参考全文的非场景部分（背景、界面风格、数据来源、限制、注意事项等）决定写法；
   测试预期仍只来自批准验收与场景原文。两者冲突时记问题表问人，不自行取舍。
3. **待实现项**（必填）— analysis.json 的 objects 中 status=missing 的项；实现时使用约定 key，测试按它定位。
4. **既有进度和收据**（恢复必填）— workflow ID、模块起始产品、最新 Green、缓冲单及检查点。

## 执行流程

首次执行场景时读取 [TDD 执行协议](references/protocol.md)，按其格式保存每次运行记录。
进入 Red 前由 campus-test 按 [检查方案](../campus-test/references/check-plan.md) 建立当前场景的检查方案；
测试和实现都沿用需求分析的场景原文，不另定一套预期。

```text
Stage 0: 核对当前施工单、边界和证据
for 当前依赖已满足的实现轮次:
    Stage 1 Red:      编写测试 → 运行 → 确认需求断言失败 → 保存阶段快照
    Stage 2 Green:    实现功能 → 以相同行为断言复验 PASS → 保存阶段快照
    Stage 3 Refactor: 整理(可选) → 确认 PASS；每轮按影响做分级回归
    Stage 4 Mutation: 独立副本破坏目标规则 → 相同测试必须检出
Stage 5: 校验逐需求证据 → 交回总流程
Stage 6: 模块回归 / 构建 / 上传（单独调用时；总流程调用时由父流程负责）
```

## 场景试运行

用户明确只试跑少量场景时，使用 [场景试运行协议](../campus-workflow/references/pilot.md)。以 `record --scenario` 保存独立场景证据；正式需求保持原状态。不能把局部收据转成整条需求收据，也不能将 unit 标为 api/db/contract 来通过正式门禁。

## 实现轮次

合并的是实现节奏，不是场景。每个场景仍有自己的检查方案、测试映射和 PASS / BLOCKED 状态；
Red 时每条需要实现的需求都要有自己的失败断言，Green 时每条需求都要覆盖全部必需测试。

按需求依赖和改动关系组织实现轮次。
同一需求包含多个场景时，先为该需求写齐必需测试再执行 Red / Green；不同需求可以批量调度，收据仍逐条保存。
当前工具只保存每条需求的有效最新阶段收据，不能用局部场景收据覆盖后声称全部场景通过。

分析固定后不原地改 objects / cells 来记录完成；实现状态关联原 key 写入运行证据。
确需改变分析或预期时，先 reset 对应检查点，再重建后续证据，不手改摘要绕过检查。

### Stage 0: 核对施工单与恢复点

核对身份、白名单、HEAD、未提交改动、依赖、analysis 与收据的输入摘要。
恢复先核对本轮证据对应哪个版本；口径变化回到需求与测试设计，受阻需求登记解除条件，其他独立需求继续。

## 阶段判据

- **有效 Red**：检查方案要求的测试均已实际运行，至少一条明示需求的行为断言在当前产品版本失败；
  已实现部分可为 PASS，其他必需用例均已执行。保留失败场景 ID 与实际结果。
- **ERROR / BLOCKED / NOT_RUN**：分别记录构建或驱动错误、必要前置条件受阻、
  未执行或跳过的必需用例；处理后重跑，再判断阶段结果。
- **Green**：使用与 Red 相同的行为断言，在当前实现和对应安装包上完成检查方案要求的测试；
  实际执行数大于零，全部必需用例 PASS，适用分支已触发且有断言证据，退出码与运行器结果一致。
- **场景 PASS**：检查方案里每个必需等价类都是 PASS。有 BLOCKED 的等价类时场景记 BLOCKED，
  不能报“通过”。人工同意暂不测只记录豁免与影响；要改变正式验收范围，须更新批准基线和方案后重新验证。
- **触发**：分支判为“已触发”时，结果必须能指回本次运行的触发证据，并对应检查方案中的分支；
  旧任务可继续关联原触发表。条件不具备记 BLOCKED。
  脚本跑完、按钮点过、运行器 OK 都不能证明分支已进入，也不能计入 PASS。
- **证据**：每次运行记录场景 ID、源码版本与未提交改动、输入 / 产物摘要、容器与实际测试环境、
  命令、起止时间、退出码、用例计数、日志和截图；详细结构见 references/protocol.md。

## 基线失败处理

- 只验证本模块本轮新增或修改的部分，以及这些改动直接影响的测试。
- 基线已有失败与当前场景无关：保留测试命令、错误输出和关联判断，继续本模块工作。
- 本轮明确要求的入口或行为缺失，初态和定位已确认：记 FAIL，可作为有效 Red。
  即使问题来自基线，也按本轮已授权的实现范围修复，不能为了绕开失败而改低预期。
- 构建、被测版本选择或驱动错误：记 ERROR，校正条件后重跑。
  必要账号、服务或数据无法取得：先在授权的隔离环境构造测试数据或本地条件，不能伪造校方身份或访问权；
  仍无法取得记 BLOCKED，记录解除条件，最晚在当前轮结束时问人；继续独立场景。mock 不证明真实集成。
  分不清“条件缺失”与“本题未实现”时，标 `[ATTRIBUTION]` 记入需求分析的问题表，
  场景先记 BLOCKED，不记 FAIL；完成诊断后按回复改判。
- 修复需要改变外部服务或超出已有授权时，先完成可执行诊断，
  提交具体改动、影响和证据，再取得相应授权。涉及受保护资料时改用合规来源，
  按 AGENTS 与 guard 协议保留记录；与本题无关的基线修复另行处理。

## 文件发现

目标文件不存在时，先列出相邻目录或搜索相关文件名，读取真实存在的文件；
仍未找到时，报告缺失文件及已检索范围，取得路径确认后继续。

### Stage 1: Red：编写测试并验证失败

- 按检查方案编写本层测试，参考 campus-test；UI 类的必需观察不能以纯逻辑、SSR 或人工通过代替自动 TDD 证据。
- 实际运行，按「阶段判据」确认有效 Red 或“已有行为满足”，保存运行证据。
- 用 team.py record 保存每条需求的 Red 收据、实际业务失败断言、命令、必测 ID、报告与阶段快照，不生成正式 commit。
- 实现前全部必需断言已满足时标 baseline_satisfied，保存 baseline / Green；产品摘要须与模块起始产品一致，不制造 Red，仍做变异验证。

### Stage 2: Green：实现功能并验证通过

- 优先做 objects 里 status=missing 的项：按约定 key 逐条建，保留对象 key；后端同时完成对应约束与本模块迁移。
- 实现状态写入私有证据，固定的 analysis 不原地修改。新发现对象或口径时回到分析、重置检查点，不自行补需求。
- 实现满足测试断言的最小功能改动。
- 用与 Red 相同的测试命令、报告路径和必测 ID 在当前输入复验同一组行为断言，保存 PASS 证据；实际构建另留 check 回执。
- 测试失败先归因。修复脚本、定位或数据条件时记录原因，并复核实现前版本的检出效果；
  改变业务预期必须有需求依据并重新建立 Red / Green 证据，不能为提高通过率删弱断言。
- 保存当前 Green、产品差异和源码摘要；mock / stub 的隔离验证与真实联调分别列出。

### Stage 3: Refactor：整理代码并复验（可选）

- 消除临时代码、统一命名，按影响范围复验 PASS。
- 整理后重新取得当前源码的 Green，保存阶段快照，不复用过期收据。baseline_satisfied 分支不修改产品。
- 无需整理时记录“无需重构”，不为流程制造代码变更。

## 分级回归

使用 `git diff --name-only` 列出本次改动，检索被改文件或符号的引用
（`rg -l "<被改符号或文件名>" <模块>/src`，或检查 import），根据引用关系确定受影响场景。

| 改动类型 | 回归范围 | 示例 |
|---|---|---|
| 本场景测试代码 | 本场景；可定位到用例时执行用例级测试 | Vitest / JUnit 的真实用例选择参数 |
| 本场景专属产品文件（新页面/组件，未被其他场景引用） | 本场景 | 新增评价区组件，仅场景一使用 |
| 被 N 个场景引用的组件 / ViewModel / 路由 / 数据模型 / 格式化工具 | 引用该改动的 N 个场景 | `CommentUtil` 被场景一/二/三引用 → 执行场景 1/2/3 |
| 公共测试基类 / helper（`ui_common`、harness） | 使用该 helper 的场景（通常为全部已完成） | 改 `scroll_until_text` → 执行全部引用场景 |
| 改全局入口 / 底部导航 / 主题 / 权限 / 依赖版本 / 构建配置 | 全部已完成场景（保守） | 改 `MainPage` 路由或 公共 package.json / Maven 配置（成员无权直接修改） |
| 只改文案或资源 | 仅本场景引用 → 本场景；共享资源 → 引用它的场景 | 改本场景的 本模块 zh-CN.ts / en.ts |
| 修复人工验收反馈的缺陷 | 该反馈对应场景 + 改动点的引用方；交付前再全量 | 滑块抖动修复 → 场景一 + 引用滑动组件的场景 |

- 每轮 Green 后执行 1 次分级回归（不是轮内每个场景各一次）；失败修复后执行 1 次复验。复验仍失败时，先定位根因。
- 回归通过后进入下一轮。
- 模块交付前执行当前版本全部可完成需求的回归及本层 build / 类型检查；已覆盖全部且输入完全相同的最新 Green 可复用。
- 实际浏览器与跨服务链路未运行的部分单列，不得报完整验收通过。当前容器已启动应用且可访问时给出地址供真人验收。

### Stage 4: 独立变异验证

按 [TDD 执行协议](references/protocol.md) 使用 mutation 命令创建独立工作树和容器，
仅破坏当前目标的产品规则，使用与最新 Green 相同的命令、报告路径和必测 ID。
变异必须关联原 Green 输入并检出目标业务失败；不修改测试，原工作树保持 Green，副本不能 submit。

### Stage 5: 校验证据并交回调度

逐条核对 version=2 收据。tdd 模式须 red / green / mutation；baseline_satisfied 须 baseline / green / mutation。
每次运行保留新 run ID、实际报告、输出与源码快照，不能手填 PASS / success 来代替运行。
tdd 检查点通过后交回 campus-workflow 的 regression 阶段，不重复父流程上传。

### Stage 6: 模块回归与交付（单独调用）

完成上面的分级回归、模块收尾回归与构建，再执行 guard 和 submit；存在 workflow 时带 --workflow。
上传模块 diff 与证据，取得网站真实缓冲单号后才称已上传。失败保留材料与恢复点。
真人审核与独立 CI 通过后由缓冲站生成正式提交，按 72 小时周期推功能分支 / 创建 MR；不直推 main。
Git 冲突由人处理，生产发布需人工审批。

## 输出

功能代码、本模块测试与中英字典、必要迁移、阶段快照或已有行为验证、
.campus/runs/ 中的实际运行证据及回归结果；总流程返回有效收据，单独交付还返回真实缓冲单号。

## 完成条件

- [ ] 本轮全部可完成需求的必需测试 PASS；无关基线失败、UI / 集成待验和外部受阻已分别留证。
- [ ] 实现场景已有有效 Red / Green 和阶段快照；已有行为满足的需求有模块起始产品验证。
- [ ] 必需用例全部执行，结果可关联到当前源码、测试、输入快照和断言。
- [ ] 待实现对象全部完成，或明确本次未完成原因和影响，沿用原 key。
- [ ] 每轮分级回归和交付前模块收尾回归通过；重构后 Green 有效。
- [ ] 独立变异关联最新 Green 并检出产品规则破坏，原工作树未被污染。
- [ ] 总流程收据已交回；单独交付确实取得缓冲单号，未提前生成 Gitee 正式交付提交或声称已合并 / 发布；GitHub 开发分支按总流程独立导出。
