# 向人提问

本文件规定 AI 什么时候问、怎么问、回复怎么回写。人怎么回答不写进 skill。

## 1. 什么时候问

只在遇到**自己定不了的口径或资源**时问；查得到的先查。

| 自己定 | 问人 |
|---|---|
| 有原文依据的 | 两种解释都成立，且会改变验收结论（含某个等价类怎样算对） |
| 已授权范围内的 | 要不要实现、算环境受限还是没做、缺陷还是需求没要求 |
| 查得到的事实（README、源码、DOM / 可访问性树） | 只有人有的东西（账号、权限、真实服务、团队信息） |

任何阶段都可以问，区别只在要不要立刻打断：

- **阻断**（不问就做不下去）：立即问。
- **非阻断**（还有独立工作可做）：需求阶段在阶段结束时一次问完；测试阶段**最晚在当前场景（合并实现时为当前轮）结束时**问，
  受影响的结论保持待确认。不能把问题留到人工验收时再提——验收交接不是提问的地方。

容器 / 服务被占、构建失败等异常先在授权范围内诊断恢复，确实需要人工资源或决定才问。

## 2. 提问格式

编号用 `H01…`，与需求问题表的 `Q / U / A` 分开。

**像对队友说话一样写**：标题就是问句；正文不加字段标签，不堆 ID、文件路径和代码键名；
要人决定的事放在前面，依据放最后一行。人读完前两行就该知道要选什么。

````markdown
### H<n> <一个问句>

<两三句话：原文怎么说、现在实际是什么、为什么自己定不了（查过什么）>

- A. <选项，用界面上看得到的说法>
- B. <选项>
- C. <选项；不超过三个>

<我倾向 X，因为……；没有依据就写“我没法推荐”。供给类改写“需要你提供……”>
<影响哪些场景，不影响什么；等你回复期间我先做什么>

依据：<问题表 ID、场景 / 等价类编号、截图或源码位置>
````

示例：

````markdown
### H01 设置里的这几个名称，要按需求改吗？

需求里叫「设置」「在线服务」「在线服务配置」，应用里现在叫「应用设置」和「云服务设置」。
需求没说要不要改名，两种理解都说得通，所以来问你。

- A. 只改在线服务相关的：列表项改成「在线服务」，页面标题改成「在线服务配置」，「应用设置」不动
- B. 三个都按需求改
- C. 都不改，保持现状

我倾向 A：需求里的「设置」更像泛指设置页，「在线服务配置」才是具体页面名。
只影响 S01、S02 里入口和标题的文字，不影响表单功能和本地曲库；等你回复期间我先做 S03。

依据：Q01；S01 第 1–2 步、S02 第 3 步；截图 boundary-settings.jpeg、boundary-api-set.jpeg
````

反例（同一个问题，读起来像填表）：
`1. 关联与事实：S01 第 1–2 步…string.json 的 SET_CLOUDSERVICE…  2. 已查与未决：…  3. 需要的决定：A 只把在线服务入口与页面标题改为…`
——标题不是问句，要选什么埋在第 3 段，代码键名和路径挡在前面。

问题有四类：

| 类型 | 问什么 | 人的回答动作 |
|---|---|---|
| 指认 | 这个名称指哪个对象 | 从候选里选一个 |
| 裁定 | 两种解释选哪个 | 选 A 或 B |
| 归因 | 环境受限、本题缺失还是范围外 | 先做诊断；只有口径仍未决才问 |
| 供给 | 账号 / 权限 / 真实服务 | 给资源 |

一次问多项时先给一张摘要表，再逐项按上面的格式展开：

```markdown
| # | 类型 | 一句话 | 我的倾向 | 影响 |
|---|---|---|---|---|
| H01 | 指认 | 「在线服务配置」指哪个页面（U01） | A：应用设置 → 在线服务 | S01 |
| H02 | 裁定 | 列表为 0 条时显示什么（Q02） | 显示空态提示 | S03#1 |
| H03 | 供给 | 登录账号 | 需要正式账号 | S04 |
```

## 3. 四条硬规则

1. 一题只问一个决定；不把实现方法交给人设计。
2. 可查的事实先查，写清实际查了什么；只有人持有的资源说明这一点即可。
3. 判断类有依据才给建议，没有就写无法推荐，不编造候选；候选不超过三个。
4. 没有回复不等于同意：不擅自改需求、范围或验收口径，不把受阻项记 PASS。

## 4. 回复之后

写入 analysis.json 的 issues（含 H 编号、原始回复与位置）及私有进度记录，回落到对应场景和等价类；旧结果保留当时版本，
不用新预期覆盖旧失败。回复已带授权时直接执行，不再重复确认。

## 5. 不要这样问

- ❌ “这个功能怎么实现？”——是能力问题，不是口径问题。
- ❌ “你能帮我确认一下这个页面吗？”——把查证推给人。
- ❌ “我遇到问题了，怎么办？”——没有现象、没有已试、没有候选。

## 本项目交接

只阻塞受影响的需求，其他独立任务继续。通过 workflow-block 记录 clarification / external / scope 和解除条件。
已固定 test-plan 时不原地改分析，应先 reset 对应检查点再重建证据。真人验收、Git 冲突和生产审批不由 AI 代签。
