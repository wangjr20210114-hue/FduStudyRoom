# 场景试运行

## 执行条件与输入

用户明确要求先跑一小部分。输入为已登记身份、模块层、现有 `Sxxx.SCxx` 场景编号及其正式父需求；不新建假的业务需求，不修改正式验收或依赖。协调人先冻结并登记试运行基线，再开展成员工作。

## Stage 0：认证、定位与确定范围

运行 `python scripts/team.py pilot d --layer backend --scenario S040.SC02`。工具核对归属并返回逐字场景、来源哈希、依赖和 `partial` 状态。施工单列出本轮只验证的规则、测试样本及未覆盖的 UI、持久化和公开契约。

## Stage 1：隔离与真实基线

创建本人 worktree 和 runner，核对 UID、只读根目录、本人可写挂载、私有目录遮罩和网络；不能降级到宿主编写成员代码。已有空业务模块可以运行所属服务的既有真实测试作为“共享服务基线”，须明确被测范围，不加恒真测试。未运行的迁移和业务集成单列。

## Stage 2：场景分析与测试方案

保留工具返回的原文及哈希，写明本轮目标、样本、观察和比较方式。只验证领域规则时使用 unit，不声称整张页面或整个场景的端到端行为已完成。尚未满足的真实跨模块依赖继续保留。

## Stage 3：RED、GREEN、REFACTOR

先有可编译的最小产品接口，编写行为断言并实际观察断言失败；编译和驱动失败不是 RED。使用 `record --scenario S040.SC02 --requirement M2-02 ...` 保存实际容器测试报告和快照。GREEN 保持相同命令、报告、断言和必测ID；必要整理后重跑。

## Stage 4：独立变异与回归

使用原 mutation 命令建立独立 worktree/runner，只破坏产品规则、不改测试，相同测试应检出。保留与 GREEN 的输入关联；原工作树保持通过。回归与构建使用当前输入，明确 unit 验证范围。

## Stage 5：结果与交接

私有输出使用 `scope=scenario_pilot`、`scenarios[场景编号].stages`，正式 `requirements` 收据不混写。保留身份、原文哈希、父需求、依赖、每轮命令/退出码/报告/快照和未覆盖项。工作成果交协调人检查；正式 submit 必须拒绝试运行格式。不能抽出或改名后上传为完整需求。GitHub/Gitee 正式交付仍按正常全量需求验收及交付流程执行。

## 完成条件

- 已选规则有真实行为 RED、相同断言 GREEN、独立变异和当前回归证据。
- 六身份的目录、凭据、模块及 runner 独立；实际隔离检查有记录。
- 试运行通过仅代表选定规则；父需求和真实 UI、持久化、集成状态未被改成完成。
- 基线缺陷与业务改动分别记录；未通过真人验收不生成 Gitee 正式提交，不自动处理 Git 冲突。
