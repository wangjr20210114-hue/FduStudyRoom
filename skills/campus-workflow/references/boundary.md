# 边界确认

## 目标

梳理本模块仓库的内容，产出两张清单：**UI 上有什么（页面 → 组件），数据上有什么（账号、外部服务、初始数据）**。
产出的都是**事实**，不含判据。判据在 campus-req 里写。
范围限于本模块涉及的页面、入口及必要依赖；其他页面保留源码索引，不强制逐页运行。

## 输入

本模块 Spec（只用来知道范围）、工程目录（取页面路由）、实际容器 / 服务地址、环境检查结果。

## 硬规则

**拿不到的项必须带「已试动作」**，统一记入「未核验与受阻项」，否则等于把活推给人。

## 执行流程

### Step 1：提取页面清单

读取本模块路由、页面与导航源码，并核对实际 DOM / 可访问性树。从页面声明、路由调用、Vue Router / Tab 等结构提取本模块涉及的页面，
登记实际路由稳定 key，每页一句描述（是什么页面、从哪进）。不是所有页面都有独立路由；
没有路由时在描述里写真实 组件分支名称、Tab 或条件分支。
**声明不证明可达，采样失败也不证明页面未实现**；走不到、拿不准的页面进「未核验与受阻项」。

### Step 2：提取组件清单

按本模块涉及的页面与状态采样，结合源码和运行树，登记组件稳定 key：名称、类型、绑定的页面。
组件名用界面文本或标识；保留需求涉及的无文本图标、图片、滑块、输入框、播放器及必要容器。
未在当前状态出现的组件不进表，列入「未核验与受阻项」，不直接推断缺失。
定位方式不在这一步确定，留给测试阶段核对。

### Step 3：确认数据边界

账号、外部服务、初始数据三类，先查本模块 README / build.md 和配置，再核验可用性。
区分已有资源、可自行构造的测试条件、需人提供的条件；不默认用 mock 替代真实链路。
同时记下数据规模：能否造出 0 条 / 1 条 / 多条、页容量多少、哪些字段可为空，供测试阶段划分等价类。
后端同时登记公开 API、可用测试库、模块 schema 与迁移条件，不能写入其他模块数据库。

### Step 4：产出

边界事实写入本层 analysis.json 的 boundary（pages/components/data/unverified），
原始 DOM / 响应 / 截图存 .campus 的私有证据目录并引用路径。无浏览器采样时明确是源码事实，不能标为运行可达。

**交出去的是材料，不是结论**。需求绑定与待实现表由 campus-req Stage 2 完成，
它复用这里的稳定 key，新增对象约定唯一 key，既有 key 不重新分配。

## 产出

- analysis.json.boundary：页面 / 组件事实、数据边界、未核验与受阻项。
- .campus 私有采样证据：真实 DOM / 可访问性树、响应与截图；无的写未运行。

## 完成条件

- [ ] 本模块相关页面都进了页面清单，每页有一句描述
- [ ] 需求涉及的组件都进了组件清单并绑定页面，无文本组件没有被漏掉
- [ ] 未观察到的组件进了「未核验与受阻项」，没有直接推断缺失
- [ ] 数据边界每项写清有没有、从哪来、谁提供；无的项写明"无"
- [ ] 数据规模写清能否造出 0 条 / 1 条 / 多条及页容量
- [ ] 拿不到的项都进了「未核验与受阻项」，写了已试动作与影响

## 与现有检查点的交接

在 workspace / baseline 后、requirements 前执行，作为 Stage 2.5；不新增 team.py checkpoint 名称。
源码采样缺口不阻止独立原文分析；必需行为的可用性与观察缺口由后续检查方案保留。
当前校验器不自动核验 boundary 扩展字段，执行会话负责真实性，不能写虚构页面或已采样状态。

首次创建 analysis.json 时保留 version/module/layer 与现有 requirements；后续需求分析合并保留 boundary，不用空文件覆盖已有内容。
