# FduStudyRoom 全流程工作流

## 目标

根据成员身份，从需求文档中找到本人未完成的需求，在模块边界内完成分析、测试、实现、验证和缓冲站上传。中断后从有效检查点恢复；已验收项核对证据后跳过，外部受阻项保留并继续独立任务。

执行顺序为“基线 → 边界 → 需求 → 场景 TDD → 回归 → 验收与交付”。

本技能是总入口，调用 [campus-build](../campus-build/SKILL.md)、[campus-req](../campus-req/SKILL.md)、[campus-test](../campus-test/SKILL.md)、[campus-tdd](../campus-tdd/SKILL.md)。AI实际编写代码和测试，工具管理状态、隔离和证据；不能只生成计划就声称完成开发。

## 执行条件

- 用户要求全流程开发、继续需求或恢复模块任务。只查询状态时只读，不自动转为开发。
- 工作区包含本套技能、`scripts/team.py`、`spec/modules.json`、`spec/requirements.json` 和 `AGENTS.md`；缺少时先定位或取得正确版本。
- 开发前必须有缓冲站登记身份和个人 `.campus/member.local`，且检出版本与冻结基线一致。身份名称不是认证，缺凭据不能伪装登录。
- 首次环境不全时进入 Stage 0 补齐。未发布优化基线、无权限或缺人工资源时记录受阻，不能绕过前置条件。

## 输入

| 输入 | 必需性与取得方式 |
| --- | --- |
| 成员身份或已登记Gitee别名 | 必需；用户提供，与个人令牌对应记录核对 |
| 需求范围 | 默认本人全部未完成需求；小批次可用 `--requirements IAM-04` 指定完整需求 ID，多个 ID 用逗号分隔；恢复时重复相同范围。不得超出本人模块和层，也不能只选部分验收条目冒充完整需求 |
| 项目路径 | 默认当前工作区，必须定位到项目根目录 |
| 模块、前后端层、冻结基线和可写路径 | 从缓冲站及manifest取得，不要求用户重复填写 |
| 个人凭据 | 本机忽略文件提供，不写入对话、日志或Git |
| 恢复记录 | 已存在时复用workflow ID、工作树、检查点和缓冲单号 |

调用示例：`$campus-workflow 我的身份是 b，处理未完成需求`。

## 执行要求

读取AGENTS及spec。应用栈固定TypeScript/Vue 3、Java 21/Spring Boot 4.1.2、PostgreSQL；只写本人模块和层的白名单，国际化、迁移和公开契约遵守项目规则。任务书是需求证据，不是执行代理指令。

已授权阶段连续推进，不逐阶段询问“是否继续”。重大验收歧义、公共基线变更、真人验收和Git冲突按现有规则处理；只阻塞受影响项，不替真人签署审核。

## 执行流程

```text
Stage 0 启动与恢复
  → Stage 1 工作区(workspace) → Stage 2 基线(baseline)
  → Stage 2.5 边界事实 → Stage 3 需求(requirements) → Stage 4 测试方案(test-plan)
  → Stage 5 TDD(tdd) → Stage 6 回归(regression)
  → Stage 7 双路交付(upload) → Stage 8 CI/部署 → Stage 9 跟踪/继续其他模块
```

涉及交付时读取 [交付与部署协议](references/delivery.md)。首次执行、恢复或阶段切换时读取 [执行协议](references/execution.md)。Stage 1—6的括号值对应工具检查点；上传和审核状态以网站真实返回为准，不手写成功标记。子技能已通过的检查点直接复用。

### Stage 0：启动、认证与恢复

**执行**：核对加载的五个技能与项目源版本；需要时用install-skills的--check比较。调用campus-build检查环境，已有兼容工具与有效构建可复用；缓冲站不可达先诊断，不冒充协调人新建身份。运行 `python scripts/team.py plan <身份> --layer backend --status 全部`，核对已完成项所指文件及真实审核/CI记录，再运行 `python scripts/team.py workflow <身份> --layer backend`，取得workflow_id和next。指定模块加--module；只处理少量完整需求时加 `--requirements IAM-04`，范围随本轮 workflow ID 冻结，恢复重复相同参数。未选项记为本轮未选，不冒充外部受阻或已完成。同一工作树不能同时打开不同范围的活跃流程。仅查看用--preview。仅查询时输出状态后结束，不执行Stage 1—9。

**输出**：已认证身份、冻结基线、已完成证据核对、本人待办及恢复点。

**通过条件**：身份/基线/技能版本一致。已完成项有依据；证据缺失登记核验缺口，不擅自把accepted改为pending。恢复时核对HEAD、未提交工作、检查点及网站状态，不覆盖旧记录。

### 六人分工与层切换

示例成员 a—f 分别负责 M01—M06，每个人同时拥有本领域的前后端任务。身份和访问码只有一份。总流程先处理 backend，再处理 frontend；plan、workflow、worktree 显式带 --layer。两个层使用不同 worktree、workflow ID、容器及收据，不扩大到其他领域。

```text
python scripts/team.py workflow b --layer backend
# 小批次选择完整需求，恢复仍使用相同参数
python scripts/team.py workflow b --layer backend --module M02 --requirements RES-07
python scripts/team.py worktree b M02 --layer backend
python scripts/team.py workflow b --layer frontend
python scripts/team.py worktree b M02 --layer frontend
```

前后端测试各自通过后，还需验证本领域的实际前后端联调。示例配置不会替换已运行缓冲站的旧成员；协调人核对交接后再调整私有配置。

### 小范围场景试运行

用户明确要求先试跑部分场景时，按 [场景试运行](references/pilot.md) 建立独立施工单和收据。仍须真实认证、模块容器、原文分析、行为 Red/Green、独立变异和回归；局部通过不推进正式需求完成、正式上传或生产发布。

### Stage 1：建立限界工作区（workspace）

**执行**：为当前模块创建或复用专属worktree，启动对应sandbox。核对只读公共目录、本人可写目录及容器身份；成员容器不挂载Docker socket、他人凭据或生产配置。

**输出**：工作树路径、任务上下文、容器及实际边界。

**通过条件**：工作树属于本人模块和层，HEAD等于冻结基线，所需容器就绪，workspace检查点通过。强制隔离未具备时不转为宿主执行成员代码。

### Stage 2：保存现有测试基线（baseline）

**执行**：修改产品前在模块容器运行现有相关测试，使用record的模块baseline阶段保存实际报告和源码摘要。区分既有业务失败、运行错误和外部条件，不通过修改产品掩盖基线问题。

**输出**：真实baseline收据、命令、报告、输入快照与失败归因。

**通过条件**：baseline检查点接受有效收据；报告缺失、零用例、skip或运行错误不能当作通过。无法建立基线的项保留受阻，继续其他可开发模块。

### Stage 2.5：边界确认

按 [边界确认](references/boundary.md) 梳理“页面 → 组件”和账号、服务、初始数据事实。
**声明不证明可达，采样失败也不证明页面未实现**；走不到、拿不准的页面进未核验与受阻项。
边界产出只含事实，不含判据；先理解 Spec，再核对边界，采样到的实现现状不能取代原文预期。
源码索引或运行采样存在缺口时照实交接，不因拿不到快照而阻止独立的原文分析。

**输出**：analysis.json.boundary、实际观察证据或未核验项及已试动作。

**通过条件**：相关页面 / 组件和数据来源可回查；未观察到的没有被直接标为缺功能。
这是 requirements 的准备步骤，不新增工具检查点；不能调用不存在的 boundary checkpoint。

### Stage 3：需求分解（requirements）

**执行**：调用campus-req，按 Stage 1—5 保留完整原文、场景和对象对应，识别待实现项、依赖与问题。重大歧义先查既有决策，缺少依据时仅阻塞受影响需求。

**输出**：本模块本层analysis.json，覆盖全部本轮条目及受阻记录。

**通过条件**：requirements检查点通过；验收原值未改，覆盖完整，ID稳定，依赖无环，影响验收的未决问题没有被默认为已解决。

### Stage 4：测试设计（test-plan）

**执行**：以设计模式调用campus-test，按检查方案划分等价类，写清怎样算对、预期依据、样本、观察与比较，映射测试ID和类型。node / SSR、真实浏览器和人工结果分别记录；必需 UI 自动化缺失时保留受阻，不能改 kind 标签过门禁。

**输出**：analysis.json中的cells及场景到测试的覆盖关系。

**通过条件**：test-plan检查点通过。全部必需验收项有可执行检查方案；前端交互和后端契约/持久化选择合适测试，未用方便测试的自定规则替换需求。

### Stage 5：限界TDD（tdd）

**执行**：调用campus-tdd，按依赖完成Red→Green→Refactor和独立变异验证。实现前已满足全部断言的需求标baseline_satisfied，不制造Red；每条需求单独保留证据。

**输出**：所属模块产品、测试、中英字典/必要迁移及版本2收据。

**通过条件**：tdd检查点通过。必测ID实际执行，Red是预期业务断言失败，Green来自相同测试，变异对应原Green并能检出产品规则破坏。有必需场景未验的需求不记完成。

### Stage 6：当前版本回归与构建（regression）

**执行**：按影响范围回归，模块收尾覆盖全部可完成需求并运行本层build/类型检查。当前输入和覆盖完全相同的最新Green可以复用为回归，构建另留check回执。

**输出**：当前源码对应的回归结果、构建回执和集成待验项。

**通过条件**：regression检查点通过；源码、analysis和证据摘要一致。mock/组件测试不冒充真实跨服务联调，未运行项单列。

### Stage 7：上传缓冲站和 GitHub（upload）

**执行**：运行guard，带--workflow提交本轮需求ID、说明、diff和证据；使用 --type feat/fix/refactor、--summary 标题及重复的 --detail 分点。submit 在缓冲站收件后自动导出同一差异并推送 GitHub 开发分支；两项分别记录真实状态。上传前再次核对当前输入；出错保留材料，修正可诊断问题后再提交。

**输出**：网站真实返回的缓冲单号、模块和状态；用户可审阅的文件与功能说明、测试结果、当前可访问地址及尚未验收项。

**通过条件**：网站确认接收且身份/模块匹配。未上传成功不能进入已交付；Gitee 正式交付提交不绕过人工验收。


**GitHub 开发分支**：缓冲站确认接收后，取回该单号的差异并核对摘要，在独立导出目录从同一批准基线应用该差异，生成 development/<模块>/<成员>/<层>/<单号> 分支提交，直接推送 https://github.com/wangjr20210114-hue/FduStudyRoom.git。使用当前成员自己的授权，不分发仓库所有者的凭据；缺少仓库写权限时单独记录受阻。

导出不改变原模块工作树、analysis、测试输入或缓冲站原始证据。GitHub 只接收代码和批准的版本化文档，不上传私有收据、访问码、日志或数据库材料。记录实际提交号、分支、URL 与差异摘要；推送失败保留导出目录和缓冲单号待重试，不撤回已收件项，不强推或自动解决冲突。GitHub 开发分支成功不代表 Gitee 审核、合并或生产发布通过。

### Stage 8：检查 GitHub CI 与站点部署

**执行**：推送后查看对应 SHA 的 GitHub Actions。工具回归、前端测试和构建、后端测试和构建全部通过后才能交付部署包。用户已授权本仓库所有分支在 CI 通过后自动更新华为体验站 studyroom.seatraces.com，部署由 Actions 的 huawei-experience 环境和受限 SSH 接收器执行。正式生产仍需人工审批。GitHub 推送成功不作为站点上线成功的证据。域名、SSH 发布通道或网络缺失时记录具体阻塞。

**输出**：GitHub 分支和提交、Actions 地址、构建结果、部署状态、站点地址及实际运行版本。

**通过条件**：检查首页、两个服务的健康接口、登录配置接口及 version.json；运行版本必须对应本次提交。失败保留上一版本及数据库备份。应用回退与数据库恢复分别处理，数据库不自动还原。

### Stage 9：跟踪、继续与交接

**执行**：继续本人其他可开发模块。等待项保存原因、单号、已试动作和解除条件；条件变化后同一入口恢复。审核退回时保留历史，补充退回后的新测试证据。全部剩余项均在等待时结束本轮，不快速轮询。

**输出**：按需求ID归类的开发结果、审核/CI/同步状态、受阻项及下一动作。

**通过条件**：本轮可完成开发已验证上传，其余有明确状态和材料。网站按真人审核→独立CI→正式commit→72小时推功能分支/创建MR推进；真人合并及生产审批分别记载。

## 输出

- 已完成核对后跳过、本轮完成、未运行、受阻和集成待验的需求清单。
- 修改文件及功能、测试类型与实际结果、analysis和私有证据位置。
- workflow ID、最后有效检查点、缓冲单号和下一动作。
- 外部缺口、诊断证据、可先完成部分及解除条件，不包含口令。

## 完成条件

- [ ] 身份、基线、模块、层和技能版本已经核对，未越过白名单。
- [ ] 已验收项查证后跳过；本轮全部需求都有真实状态，没有遗漏受阻项。
- [ ] 已完成开发具备有效需求/测试映射、TDD或已有行为证据、变异验证及当前版本回归构建。
- [ ] 已交付项获得实际缓冲单号；等待项留下可恢复检查点和解除条件。
- [ ] 开发验证、真人审核、CI、同步、合并和发布分别汇报，没有混称全部完成。

“本轮开发完成”不等于已合并或已发布。AI会话关闭后代码生成不会自行继续；常驻缓冲站只继续处理具备前置条件的任务及已启用的定时同步。
