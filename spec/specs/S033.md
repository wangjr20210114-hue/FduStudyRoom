# 查看我的预约历史，并重新选择预约

> 业务需求草案；页面和按钮名称用于说明计划中的功能，不表示已经实现。

<a id="s033sc01"></a>

## 场景一

### 场景概述

用户打开自己的预约历史，翻页时记录按固定顺序展示，不重复不漏项；直接请求他人的详情也会被拒绝。

### 操作步骤与预期结果

1. user1和user2各有多笔不同状态预约。
2. user1打开“我的预约历史”，列表只显示自己有权看的记录。
3. 在同一份查询数据中连续翻页，记录按开始时间和编号排序，不重复或漏项。
4. user1直接请求user2某笔详情时，系统拒绝，不泄露内容。

## 场景二

### 场景概述

历史记录里的再次预约只帮忙填入资源和时长，提交时仍检查当前规则，不复活旧记录或复制旧占用。

### 操作步骤与预期结果

1. 过去A01曾预约成功，如今已停用，或最长时长已改为2小时。
2. 用户在原3小时历史记录上点击“再次预约”，页面带入资源与时长。
3. 用户提交，系统以新业务编号按当前规则判断并拒绝。
4. 旧预约和旧占用不会复活，也不把过去的成功状态直接复制。

<details>
<summary>场景编号与精确规则补充（S033.SC02）</summary>

- 场景名称：再次预约会重新检查当前规则
- 场景编号：S033.SC02

**对应的业务要求**

- M1-08.AC2：再次预约重新检查当前规则，不复制旧占用

**精确条件**

- 历史A01曾预约成功，当前其已停用或最长时长改2

**精确动作**

- 点击再次预约并提交原3小时时段

**结果与约束**

- 仅预填资源与时长；创建新业务ID并按当前规则拒绝，不复活旧占用或复制旧成功状态

</details>

## 场景三

### 场景概述

预约历史按上海时间显示日期。用户没有记录时显示空列表，已有记录则能查看状态、签到和取消原因。

### 操作步骤与预期结果

1. 打开一笔其UTC时间对应上海次日的记录，日期及筛选均归到上海的正确日期。
2. 查看记录，可见历史状态、签到信息和取消原因。
3. 另一个没有历史的用户打开同一页面，看到0条记录，不显示编造的演示预约。

<details>
<summary>场景编号与精确规则补充（S033.SC03）</summary>

- 场景名称：日期按上海时间显示，没有记录就显示空
- 场景编号：S033.SC03

**对应的业务要求**

- M1-08.AC3：翻页不漏不重，日期时间显示正确

**精确条件**

- 一个UTC时间对应上海次日；另一用户无历史

**精确动作**

- 查看日期筛选及空页面

**结果与约束**

- 按Asia/Shanghai归日，空结果为0条而非虚构样例；历史状态/签到/取消原因可见

</details>

## 场景四

### 场景概述

有预约管理读取权限的管理员，可以按教室、座位和时间查询运营明细；普通用户不能借管理列表查看他人预约。

### 操作步骤与预期结果

1. 两个普通用户各有预约，admin1有管理读取权限，user1没有。
2. admin1打开管理列表，选择教室、座位和时间范围查询。
3. 结果包含范围内预约时段、状态、签到、违约及必要的用户标识。
4. user1尝试同样的管理查询，被拒绝，不返回他人记录。

<summary>场景编号与精确规则补充（S033.SC04）</summary>

- 场景名称：有权限的管理员可以查看预约管理明细
- 场景编号：S033.SC04

**对应的业务要求**

- M1-08.AC1：本人只能看本人历史；管理员另有授权才可查看管理信息
- SUP-03.AC2：管理员按权限查看，无数据时不编造数字

**精确条件**

- admin1有预约管理读取权限，user1没有；两普通用户各有预约

**精确动作**

- 按教室、座位和时间范围查询管理列表

**结果与约束**

- 只有授权管理员返回范围内预约时段、状态、签到/违约和最小化用户标识；普通用户拒绝且不泄漏他人记录

</details>
