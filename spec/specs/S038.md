# 有资格的用户提交整间教室申请

> 业务需求草案；页面和按钮名称用于说明计划中的功能，不表示已经实现。

<a id="s038sc01"></a>

## 场景一

### 场景概述

有整室申请资格的用户填写教室、时段和用途，提交后得到待审批申请，此时不表示已经订到教室。

### 操作步骤与预期结果

1. applicant1已获申请权限和资格，打开整室申请页面。
2. 选择R101、10:00—12:00，用途填写“课程讨论”，点击提交。
3. 系统保存申请人、教室、时段和用途，生成本人待审批申请。
4. 页面不显示已通过或已占用教室。

<details>
<summary>场景编号与精确规则补充（S038.SC01）</summary>

- 场景名称：填好教室、时间和用途后，进入待审批
- 场景编号：S038.SC01

**对应的业务要求**

- M2-01.AC1：先检查权限和资格，普通用户不能自己给自己资格
- M2-01.AC2：检查申请人、教室、时段和用途
- M2-01.AC3：提交后只是待审批，不说已经通过或订到教室

**精确条件**

- applicant1已获权限和can_apply_room=true；R101存在

**精确动作**

- 提交R101的10:00—12:00及用途“课程讨论”

**结果与约束**

- 创建本人待审批申请，保存申请人/时段/用途，界面不显示已占用或已审批通过

</details>

<a id="s038sc02"></a>

## 场景二

### 场景概述

无整室资格的用户在请求中自称有资格或冒充他人，系统仍按实际登录身份拒绝，不创建申请或占座。

### 操作步骤与预期结果

1. user1没有整室申请资格。
2. user1提交请求，把资格填为有，并把申请人写成applicant1。
3. 系统仍以user1检查并拒绝，不生成申请或资源占用。

<details>
<summary>场景编号与精确规则补充（S038.SC02）</summary>

- 场景名称：自己在请求里填写资格，不能获得申请权限
- 场景编号：S038.SC02

**对应的业务要求**

- M2-01.AC1：先检查权限和资格，普通用户不能自己给自己资格

**精确条件**

- user1无整室资格

**精确动作**

- 在请求体填写can_apply_room=true和applicant1身份后提交

**结果与约束**

- 仍按user1拒绝；不建申请、不占座，不通过前端伪造资格

</details>

<a id="s038sc03"></a>

## 场景三

### 场景概述

有资格的申请人填写空用途、无效教室或不合理时段时，系统指出输入问题，不留下半份申请或占用。

### 操作步骤与预期结果

1. applicant1打开整室申请页面。
2. 分别提交空用途、不存在教室、结束早于开始以及超出开放时间的请求。
3. 每次均提示输入问题，不创建部分申请，也不占用资源。

<details>
<summary>场景编号与精确规则补充（S038.SC03）</summary>

- 场景名称：用途空着、教室不对或时间不合理，都不能提交
- 场景编号：S038.SC03

**对应的业务要求**

- M2-01.AC2：检查申请人、教室、时段和用途
- M2-01.AC3：提交后只是待审批，不说已经通过或订到教室

**精确条件**

- applicant1有资格

**精确动作**

- 分别提交空用途、不存在教室、结束早于开始或超出开放时段

**结果与约束**

- 各次输入校验失败；没有部分申请或资源占用

</details>
