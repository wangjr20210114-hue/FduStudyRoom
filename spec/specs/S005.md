# 管理员修改账号权限和使用资格

> 业务需求草案；页面和按钮名称用于说明计划中的功能，不表示已经实现。

<a id="s005sc01"></a>

## 场景一

### 场景概述

管理员修改账号权限时使用最新资料。第一次授权成功后，另一份旧版本修改不能覆盖它，原账号的旧登录状态也随权限变化失效。

### 操作步骤与预期结果

1. user1已登录，权限资料当前为第7版。
2. 管理员按第7版资料保存授权，系统生成新的权限版本。
3. 另一份修改继续携带旧的第7版提交，系统提示资料已变化，不覆盖刚保存的结果。
4. user1原来的登录状态失效，不能继续沿用旧权限操作。

<details>
<summary>场景编号与精确规则补充（S005.SC01）</summary>

- 场景名称：两个人同时修改权限时，不能互相覆盖
- 场景编号：S005.SC01

**对应的业务要求**

- IAM-03.AC1：按最新版本修改授权或停用账号，旧登录权限随之失效

**精确条件**

- user1当前authVersion=7且已登录

**精确动作**

- admin1以expectedAuthVersion=7授权后，再以7重复提交变更

**结果与约束**

- 首次成功为新版本；旧版本更新冲突，旧会话失效；不会覆盖第一次结果

</details>

<a id="s005sc02"></a>

## 场景二

### 场景概述

院系和整室申请资格由管理员核实。普通用户在注册或个人资料请求中自行填写这些资格，不会得到受限教室或整室申请权限。

### 操作步骤与预期结果

1. user1尚未被核实为CS院系，也没有整室申请资格。
2. user1在注册或个人修改请求里填写CS并声明有整室申请资格，系统拒绝自行授权，资格不变。
3. 管理员核实情况后，通过管理功能正式授权。
4. 只有管理员确认后的资格，才用于受限教室和整室申请的检查。

<details>
<summary>场景编号与精确规则补充（S005.SC02）</summary>

- 场景名称：院系和整间教室申请资格由管理员确认
- 场景编号：S005.SC02

**对应的业务要求**

- IAM-03.AC2：普通用户不能自己声称有院系或整室申请资格
- USR-06.AC2：院系和整室资格由管理员维护，本地注册不能声称已验证复旦身份

**精确条件**

- user1未被核实CS院系且can_apply_room=false

**精确动作**

- user1在注册或个人修改请求中提交CS和can_apply_room=true

**结果与约束**

- 拒绝自授，资格不变；admin1核实并授权后才供后续受限资源和整室申请使用

</details>

<a id="s005sc03"></a>

## 场景三

### 场景概述

管理员停用账号后，该用户不能重新登录，也不能沿用旧登录信息操作；原预约历史仍保留与账号的对应关系。

### 操作步骤与预期结果

1. 管理员打开已有预约历史的user1账号。
2. 管理员点击停用，系统保存账号停用状态。
3. 用户重新登录或使用停用前的登录信息进行受保护操作，系统均拒绝。
4. 查询过去记录时，预约仍对应原账号，不删除历史引用。

<details>
<summary>场景编号与精确规则补充（S005.SC03）</summary>

- 场景名称：账号停用后不能使用，过去的记录仍保留
- 场景编号：S005.SC03

**对应的业务要求**

- IAM-03.AC1：按最新版本修改授权或停用账号，旧登录权限随之失效

**精确条件**

- user1已有预约历史

**精确动作**

- admin1停用user1，随后重用旧会话登录/操作

**结果与约束**

- 新登录和旧会话敏感操作均拒绝；历史记录保留用户引用

</details>
